## 1. Архитектура рантайма

### [Accepted] Видимая перезарядка/отдача, шаг 1 — отдача затвора пистолета (2026-09-26)
Контекст: пользователь предложил сделать видимую перезарядку/отдачу вместо чисто таймерной —
у каждого оружия модель уже состоит из двух мешей (та же схема Mesh1/Mesh2, что и у патронов).
Для пистолета — отдача затвора на выстрел (Mesh1 = верхняя часть/затвор, подтверждено
пользователем явно), для винтовки/дробовика позже — анимация перезарядки (магазин/дозарядка
патрона), другой триггер и другой шаг, делаем по очереди.
Решение (только пистолет на этом шаге):
- Новый `Assets/Scripts/Weapons/WeaponCore/SlideRecoilAnimator.cs` — на `slideTransform` играет
  корутину: локально смещается на `recoilLocalOffset` (по умолчанию `(0,0,-0.05)` в локальных
  координатах меша) за `recoilDuration` (0.04с), затем плавно возвращается за `returnDuration`
  (0.08с). Простая корутинная анимация без Animation-клипов/Mecanim — в проекте для оружия
  анимации нигде так и не делались (только процедурные скрипты вроде `WeaponSway`), держим тот
  же стиль.
- В `Pistol.prefab` добавлена ссылка на трансформ Mesh1 пистолета: исходная модель
  (`Assets/Packages/Weapons/pistol.obj`, guid `c1232b0a1b78ddf44bd877453fb7a84c`) по своей мете
  раскладывается как `fileID 100000/400000 = Mesh1_Group2_Group1_Model` (наконечник/затвор),
  `100002/400002 = Mesh2` (нижняя часть), `100004/400004 = RootNode` (этот один был уже
  использован раньше — именно его двигали/масштабировали при размещении модели, он же
  переименован в "pistol" в иерархии). Ни один из двух мешей раньше не был доступен как
  самостоятельная ссылка из `Pistol.prefab` — добавлена новая "stripped"-ссылка на Transform
  Mesh1 (`fileID 400000`) по той же схеме, что уже использована для RootNode.
- `WeaponController` резолвит `SlideRecoilAnimator` через `GetComponent` (как `CasingEjector`) и
  вызывает `PlayRecoil()` в `Shoot()`, безопасно (`?.`) для оружия без этого компонента.
Смещение/тайминг подобраны примерно, без визуальной проверки (нет доступа к редактору) — почти
наверняка потребуют подстройки на глаз, как и точки выброса гильз ранее.
Не проверено в редакторе.
Файлы: `SlideRecoilAnimator.cs` (новый), `Pistol.prefab`, `WeaponController.cs`.

### [Accepted] Видимая перезарядка, шаг 3 — дозарядка патрона у дробовика (2026-09-26)
Контекст: последний шаг видимой перезарядки/отдачи (см. записи про пистолет и винтовку выше).
Уточнил механику заранее: триггер — каждый выстрел (`WeaponController.Shoot()`, как у пистолета),
одно движение туда-обратно на Mesh2, а не цикл в несколько повторов — оказалось, что это ровно
та же схема, что уже сделана для пистолета.
Решение: никакого нового кода — переиспользован существующий `SlideRecoilAnimator.cs` как есть
(общий, ничего специфичного под пистолет там не было). Модель дробовика (`shotgun.obj`, guid
`8c2fd90275a7de3459350019dcb88783`) раскладывается по той же схеме, что и pistol.obj:
`100000/400000 = Mesh1`, `100002/400002 = Mesh2`, `100004/400004 = RootNode`. Ни один из мешей
раньше не был доступен как отдельная ссылка из `ShotgunInHand.prefab` — добавлена новая
"stripped"-ссылка на Transform Mesh2 (`fileID 400002`) по той же схеме, что и раньше для пистолета
(Mesh1) и RootNode. `WeaponController` уже резолвит `SlideRecoilAnimator` через `GetComponent` и
вызывает `PlayRecoil()` в `Shoot()` безусловно (после `casingEjector?.Eject()`) — сработает для
любого оружия с этим компонентом, включая дробовик, без правок кода.
Смещение/тайминг (`recoilLocalOffset: (0,0,-0.03)`, `recoilDuration: 0.05`, `returnDuration: 0.12`)
подобраны вслепую, скорее всего потребуют подстройки на глаз через инспектор.
Не проверено в редакторе.
Файлы: `ShotgunInHand.prefab`.
Update (2026-09-26): пользователь уточнил — нужно не просто туда-обратно одним мешем, а составное
движение: ствол поднимается вверх (весь корпус оружия, как будто дробовик передёргивают вручную),
во время подъёма/удержания — дозарядка (Mesh2 туда-обратно), затем опускание обратно. Это уже не
укладывается в общий `SlideRecoilAnimator` (он про одну деталь, без поворота всего оружия) — замена
на строгую последовательность фаз, по той же логике, что и наклон винтовки при перезарядке (см.
записи выше): поднять → сдвинуть Mesh2 туда → сдвинуть обратно → опустить, всё строго друг за
другом, а не параллельно.
Решение: новый `Assets/Scripts/Weapons/WeaponCore/PumpActionAnimator.cs` — `PlayPumpAction()`
вызывается из `WeaponController.Shoot()` (аналогично `slideRecoilAnimator?.PlayRecoil()`, добавлено
рядом, `pumpActionAnimator?.PlayPumpAction();`). В `ShotgunInHand.prefab` компонент
`SlideRecoilAnimator` заменён на `PumpActionAnimator` (та же ссылка на Transform Mesh2, добавленная
шагом раньше).
Файлы: `PumpActionAnimator.cs` (новый), `WeaponController.cs`, `ShotgunInHand.prefab`.

### [Accepted] Анимации на выстрел (затвор/помпа) не должны рваться при быстром кликанье — но кулдаун по времени специально не трогаем (2026-09-26)
Контекст: при быстром кликанье кнопкой стрельбы (быстрее, чем длится анимация помпы дробовика)
`PlayPumpAction()`/`PlayRecoil()` останавливали текущую корутину и запускали её заново — визуально
меш/оружие резко "прыгали" на исходную позицию и снова начинали движение. Разбирая причину, нашёл,
что `WeaponController.CanShoot()` вообще не проверяет время с прошлого выстрела — кулдаун между
выстрелами (`WaitForSeconds` в `PlayerShoot.ShootRoutine()`) действует только ВНУТРИ одного
удержания кнопки; каждое новое нажатие (`OnFireStarted`) стартует стрельбу заново без проверки
интервала, то есть частым кликаньем скорострельность можно обходить.
**Явное решение пользователя: так и должно оставаться** — "в реальном мире можно быстро нажимать
на спусковой крючок и стрелять быстрее или наоборот", кулдаун по времени в `CanShoot()`
сознательно НЕ добавляется. Это не баг, а осознанный гейм-дизайн: скорострельность полуавтоматов
ограничена только тем, как быстро жмёт игрок, а не искусственным таймером.
Решение (только визуальный уровень, стрельбу/урон не трогает): `SlideRecoilAnimator.PlayRecoil()`
и `PumpActionAnimator.PlayPumpAction()` теперь игнорируют повторный вызов, если анимация уже
играет (`if (coroutine != null) return;` вместо стоп+рестарт). Если выстрел прилетает быстрее,
чем анимация успевает доиграть — визуал для этого конкретного выстрела просто не проигрывается
(не обрывается и не дёргается), сам выстрел/урон/патроны обрабатываются как обычно, независимо
от анимации.
Файлы: `SlideRecoilAnimator.cs`, `PumpActionAnimator.cs`.
Update (2026-09-26): пользователь поправил — визуального "не перезапускать анимацию" мало.
Для дробовика это должно быть настоящим геймплейным ограничением: дробовик физически не может
выстрелить снова, пока не передёрнута помпа — "выстрел → анимация → выстрел" строго
последовательная цепочка, а не просто красивая картинка поверх свободной стрельбы. Для пистолета
всё наоборот: скорострельность от частого кликанья — осознанная фича, её трогать нельзя (см.
запись выше).
Решение: `PumpActionAnimator` получил `public bool IsPlaying => pumpCoroutine != null;`.
`WeaponController.CanShoot()` теперь дополнительно проверяет `pumpActionAnimator.IsPlaying` (если
компонент вообще есть на этом оружии — у пистолета его нет, поэтому пистолет не затронут вообще)
и возвращает `false`, пока анимация не доиграла — `PlayerShoot.StartFiring()`/`ShootRoutine()`
это уже проверяют перед каждым выстрелом, так что дробовик просто не выстрелит, если игрок
кликнет раньше времени (клик молча игнорируется, не ошибка). Ограничение по кулдауну времени
(`CanShoot()` на основе `FireRate`) по-прежнему не добавлено — блокировка идёт только от
реального состояния анимации помпы, не от искусственного таймера.
Файлы: `PumpActionAnimator.cs`, `WeaponController.cs`.

### [Accepted] Видимая перезарядка дробовика "из ниоткуда" при пустом магазине — доделана заправка патронов по одному в нижний лоток (2026-09-26)
Контекст: дозарядка патрона между выстрелами (`PumpActionAnimator`) уже работала, но полная
перезарядка при пустом магазине шла через общий `PlayerReload` без какой-либо анимации —
патроны просто появлялись. Пользователь показал скриншотом нижний лоток заряжания дробовика
(на "брюхе" ресивера) и попросил: наклон оружия (как у винтовки) + патроны, заезжающие туда по
одному, ровно столько раз, сколько реально дозаряжается.
Уточнил заранее (пользователь попросил переспрашивать при неясности — см. отдельную заметку в
памяти): (1) нужен видимый патрон, а не только движение механизма — да, отдельная модель;
(2) число циклов — ровно фактическое количество дозаряжаемых патронов, не фиксированное.
Решение:
- `PlayerReload.cs`: расчёт `ammoNeeded`/`ammoAvailable` перенесён из конца `ReloadRoutine`
  (после ожидания) в начало `Reload()` (до ожидания) и сохранён в новое публичное свойство
  `PendingReloadAmount` — раньше это число было доступно только В КОНЦЕ перезарядки, а анимации
  нужно знать его сразу на старте, чтобы посчитать, сколько циклов заряжания патрона проиграть.
  Само значение не меняется (ничего не может повлиять на патроны за эти 2 секунды, стрельба и
  так блокируется на время перезарядки).
- Новый `Assets/Scripts/Weapons/WeaponCore/ShotgunReloadAnimator.cs` — подписывается на тот же
  `PlayerReload.OnReloadStarted` (как и `MagazineReloadAnimator` у винтовки). На старте: наклон
  оружия один раз (наверх, `tiltLocalEulerAngles`), затем `PendingReloadAmount` циклов
  "патрон появляется у лотка → едет в лоток → исчезает (дозаряжен) → короткая пауза", наклон
  держится всё это время, в конце — обратный наклон один раз. Время на один патрон считается
  адаптивно (`(ReloadDuration - наклон - обратный наклон) / количество патронов`, зажато в
  `[minShellDuration, maxShellDuration]`), чтобы длинная перезарядка (много патронов) и короткая
  укладывались в общую `ReloadDuration` без рассинхрона.
- Патрон — ОДИН переиспользуемый визуальный объект (`LoadingShell`, изначально выключен),
  переиспользует уже готовую модель гильзы дробовика (`ammo_shotgun.obj`, meш
  `638807964d8c6ca45ae78efd83763bb1`, 3 материала — та же, что использовалась для гильзы дробовика
  раньше). Без пула и без физики (Rigidbody/Collider) — он не падает и не сталкивается ни с чем,
  просто едет по прямой между двумя локальными позициями и прячется; патроны заряжаются по
  одному последовательно, а не одновременно, так что пул из нескольких инстансов не нужен.
- Новая пустая точка `ShotgunLoadingGatePoint` (сосед `ShotgunBulletSpawnPoint`/
  `ShotgunCasingEjectPoint` в узле `Resources`) — представляет нижний лоток заряжания; `LoadingShell`
  висит под ней, локальная позиция `(0,0,0)` = "патрон дозаряжен/сидит в лотке", старт анимации —
  `shellStartLocalOffset` ниже (имитация "патрон подносят снизу рукой").
Позиция лотка (`{0, -0.015, -0.015}`), стартовое смещение патрона и все тайминги — подобраны
вслепую по скриншоту, без доступа к редактору, почти наверняка потребуют подстройки на глаз.
Не проверено в редакторе.
Файлы: `PlayerReload.cs`, `ShotgunReloadAnimator.cs` (новый), `ShotgunInHand.prefab`.
Update (2026-09-26): пользователь заметил на цепочке "последний выстрел → зарядка патронов →
быстрый поворот" что-то не то, попросил найти причину самому. Нашёл: `autoReloadHandler?.
TryAutoReload()` в `WeaponController.Shoot()` вызывается РАНЬШЕ, чем `pumpActionAnimator?.
PlayPumpAction()` — то есть на выстреле, который опустошает магазин, авто-перезарядка запускается
СИНХРОННО, ещё внутри того же вызова `Shoot()`, ДО того как помпа этого же выстрела вообще
успевает стартовать. `PumpActionAnimator` (подъём/опускание ствола на выстрел) и
`ShotgunReloadAnimator` (наклон на перезарядку) — два независимых компонента на одном и том же
`GameObject`, оба крутят один и тот же `transform.localRotation`, и на последнем выстреле их
корутины стартуют почти одновременно, деря друг у друга поворот оружия.
Пользователь подтвердил желаемую цепочку: выстрел → помпа доигрывает ПОЛНОСТЬЮ → наклон →
зарядка патронов → наклон обратно, без пересечения по времени.
Решение: `ShotgunReloadAnimator` резолвит `PumpActionAnimator` через `GetComponent` и в начале
`ReloadRoutine` ждёт (`while (pumpActionAnimator.IsPlaying) yield return null;`), пока помпа не
доиграет, и только потом выключает `WeaponSway` и начинает свой наклон. Оба аниматора больше не
работают с поворотом оружия одновременно ни при каких обстоятельствах.
Не проверено в редакторе.
Файлы: `ShotgunReloadAnimator.cs`.
Update (2026-09-26): пользователь проверил — не помогло, порядок в цепочке остался прежним.
Копнул глубже: сам фикс (ожидание `IsPlaying`) был правильным по идее, но проверялся В НЕ ТО
ВРЕМЯ. `StartCoroutine` выполняет тело корутины синхронно до первого `yield` — то есть когда
`autoReloadHandler?.TryAutoReload()` синхронно доходит до `ShotgunReloadAnimator`, мой
`while (pumpActionAnimator.IsPlaying)` срабатывает МГНОВЕННО. А в `WeaponController.Shoot()`
`TryAutoReload()` стоял РАНЬШЕ `pumpActionAnimator?.PlayPumpAction()` — то есть на момент этой
проверки помпа ещё физически не запущена (`IsPlaying` уже `false`, ждать нечего), и только
ПОСЛЕ этого в том же `Shoot()` вызывается `PlayPumpAction()`, которая наконец стартует помпу —
слишком поздно, наклон перезарядки уже пошёл параллельно.
Настоящее решение: переставлен порядок вызовов в `WeaponController.Shoot()` —
`autoReloadHandler?.TryAutoReload()` перенесён в самый конец метода, ПОСЛЕ
`pumpActionAnimator?.PlayPumpAction()` (и после `casingEjector?.Eject()`/`slideRecoilAnimator?.
PlayRecoil()`). Теперь к моменту, когда авто-перезарядка синхронно достаёт до
`ShotgunReloadAnimator`, помпа уже точно запущена, и ожидание `IsPlaying` реально ждёт.
Файлы: `WeaponController.cs`.

Контекст: у пистолета изначально не было отдельного меша обоймы (только Mesh1 затвор + Mesh2

  (`fileID: 10202, guid: 0000000000000000e000000000000000`, стандартная ссылка на builtin-меш,

  винтовки.
- Новый пул `PistolMagazinePool.prefab` (poolSize 3).
- `MagazineReloadAnimator` подключён к `Pistol.prefab` как есть, без изменений кода — уже

### [Accepted] Прыжок гасил скорость спринта мгновенно — нужно было сохранять её в полёте (2026-09-26)
Контекст: пользователь захотел два разных прыжка — обычный без шифта, и "прыжок с разбега" с
зажатым шифтом, где скорость бега сохраняется в полёте (даёт более длинный прыжок), вместо
мгновенного падения до обычной скорости ходьбы в момент отрыва от земли.
Причина: `PlayerMovement.Move()` пересчитывает горизонтальную скорость КАЖДЫЙ кадр из
`playerRun.IsRunning() ? runSpeed : walkSpeed` — отдельной "инерции"/сохранённой скорости в
проекте нет вообще, движение полностью управляется текущим вводом+флагом каждый кадр. А
`PlayerRun.CanRun()` требовал `controller.isGrounded` БЕЗУСЛОВНО:
`moveInput != Vector2.zero && isHoldingRunButton && controller.isGrounded` — то есть одно и то же
условие использовалось и для "можно НАЧАТЬ бег", и для "можно ПРОДОЛЖАТЬ бег". В момент прыжка
`isGrounded` становится `false`, `isRunning` тут же гаснет — отсюда мгновенное падение скорости.
Решение: `CanRun()` разделён на два случая. На земле — как раньше (нужен ввод + зажатая кнопка).
В воздухе — `isGrounded` не проверяется, вместо этого спринт продолжается, только если он УЖЕ
был активен на момент отрыва от земли (`isRunning && isHoldingRunButton`, где `isRunning` — это
значение с предыдущего кадра, естественная "память" без доп. полей). Это даёт ровно два прыжка:
без шифта — обычный (isRunning и так был false, в воздухе останется false); с зажатым шифтом на
разбеге — скорость бега сохраняется всё время полёта, пока шифт не отпущен. Начать бег в воздухе
(если жать шифт уже после отрыва от земли) по-прежнему нельзя — так и задумано.
Не проверено в редакторе.
Файлы: `PlayerRun.cs`.

### [Accepted] Смена оружия с зажатой кнопкой стрельбы наследовала скорострельность старого оружия (2026-09-26)
Контекст: пользователь заметил — если стрелять из винтовки с зажатой кнопкой и в этот момент
подобрать/переключить дробовик (или пистолет), новое оружие продолжает стрелять со скоростью
СТАРОГО, пока не опустеет магазин.
Причина: в `PlayerShoot.ShootRoutine()` интервал между выстрелами (`WaitForSeconds`) считался
ОДИН раз при запуске корутины стрельбы: `var wait = new WaitForSeconds(GetSecondsPerShotSafe());`
до цикла, и переиспользовался на каждой итерации `yield return wait`. Пока кнопка зажата,
`StartFiring()` не перезапускает корутину повторно (`if (shootingCoroutine != null) return;`) —
она просто продолжает крутиться, а `SetCurrentWeapon()` меняет `currentWeapon`, чей `Shoot()`
вызывается, но НЕ пересчитывает уже закэшированный `wait`.
Решение: `GetSecondsPerShotSafe()` пересчитывается на каждой итерации цикла (создаётся новый
`WaitForSeconds` перед каждым `yield return`), а не один раз до цикла — скорострельность всегда
берётся у актуального `currentWeapon` на момент паузы между выстрелами.
Не проверено в редакторе.
Файлы: `PlayerShoot.cs`.

между кадрами — `OnTriggerEnter` просто не успевает сработать.

пускает `Physics.Raycast` от прошлой позиции снаряда до текущей (по вектору смещения за кадр) и,
если по пути что-то есть, вручную вызывает `HandleHit()` — тот же метод, что и обычный
`OnTriggerEnter`, со всей его существующей логикой (игнор пуль своего слоя/гильз, урон
Enemy/Environment, деспавн). `previousPosition` сбрасывается в `OnEnable()` (важно: если
сбрасывать её только в `Awake()`, при повторном заборе объекта из пула первый `FixedUpdate`
после респавна проверял бы луч от СТАРОЙ позиции у пула до новой точки спавна — ложное
попадание по всему, что между ними). Правка в общем базовом классе — распространяется сразу на
пистолет/винтовку/дробовик/ракетницу (`RocketBulletController` ничего не переопределяет в
`FixedUpdate`, наследует проверку, а её собственный override `HandleHit` вызывается как обычно
через виртуальную диспетчеризацию).
Не проверено в редакторе.

`Bullets`(10) на встроенный `Ignore Raycast`(2) — Unity исключает этот слой из

от пола не завязаны на этот слой — идут через `m_ExcludeLayers` коллайдера (Update выше) и
независимую от рейкастов коллиз-матрицу, поэтому не пострадали. `m_ExcludeLayers` оставлен как
есть — лишняя защита от физического толчка не мешает.

  оси, перпендикулярной `baseDirection` — а затем результат прокручивается ("spin") ПОЛНОСТЬЮ

### [Accepted] Фикс: пули летят "не из ствола" при близких врагах (2026-09-20)
Контекст: давно известный пользователю баг — когда враг стоит почти вплотную к игроку, пули
визуально вылетают не из дула оружия, а как будто из точки где-то сбоку. Пользователь не мог
понять причину и просил поискать её, не привязывая к конкретному узлу заранее.
Причина: `WeaponController.GetShootDirection()` пускал луч прицеливания из позиции камеры
(`Camera.main.ViewportPointToRay` от центра экрана), а направление пули считал как
`(hit.point - spawnPoint.position).normalized` — то есть заставлял пулю "довернуть" траекторию
от дула до точки, куда смотрит камера. Дуло (`bulletSpawnPoint`, например
`PistolBulletSpawnPoint` в `Pistol.prefab`) смещено от камеры в сторону и вперёд
(`m_LocalPosition: {x: 0.869, y: -0.078, z: 1.252}` в локальных координатах оружия) — обычная
поза оружия-в-руке в FPS. На дальней дистанции этот доворот незаметен (угол крошечный), но
когда цель почти вплотную, точка попадания луча оказывается совсем рядом с камерой, а дуло
всё так же смещено в сторону на фиксированное расстояние — довернуть траекторию до этой
близкой точки можно только под резким боковым углом от дула, отсюда и видимый эффект "пуля
стартует сбоку".
Решение: если дистанция до цели (`hit.distance`) меньше или равна реальному смещению дула от
камеры (`Vector3.Distance(ray.origin, spawnPoint.position)`, считается динамически, а не
хардкодом — подстраивается под любое оружие с любым смещением ствола без ручной настройки),
довороты не делаем — стреляем вдоль направления взгляда камеры (`ray.direction`), как и в
ветке "луч ни во что не попал". За порогом смещения — прежняя точная конвергенция на точку
попадания (не трогали, дальняя стрельба в прицел работала верно).
Эта же функция (`baseDirection`) используется и дробовиком (`ShotgunBulletController.Fire`
получает результат `GetShootDirection()` параметром) — фикс автоматически чинит и его.
Файлы: `WeaponController.cs`.
Не проверено вручную в редакторе — только правка в скрипте, сцену/префабы не трогал.

Initialize()` никогда не поворачивал модель пули по направлению её реального движения — пуля
спавнилась с `spawnPoint.rotation` (разворот ствола) и оставалась в нём навсегда, при этом её

маленький, разница в развороте модели незаметна. На близкой дистанции доворот резкий (см.
причину выше) — модель визуально "смотрит" вперёд по стволу, а физически стремительно летит
вбок/назад относительно этого разворота, что и читается глазом как "пуля вылетела не оттуда".
Решение: `GetShootDirection()` возвращена к исходному виду (без спец-случая по
`muzzleOffset`/`hit.distance`) — конвергенция на точку попадания работает всегда, как и
раньше, урон засчитывается корректно на любой дистанции. Вместо этого в
`BaseBulletsController.Initialize()` добавлен `transform.rotation =
Quaternion.LookRotation(direction.normalized)` — модель пули теперь всегда визуально
разворачивается точно по направлению своей фактической скорости, а не по развороту ствола.
Это общий для всех типов пуль метод (пистолет/винтовка/дробь/ракета — `RocketBulletController`
не переопределяет `Initialize`), фикс автоматически покрывает все виды оружия одним изменением.
Файлы: `WeaponController.cs` (откат), `BaseBulletsController.cs`.

относительно дула — пуля летит в сторону игрока/камеры, а не вперёд. Ровно это и означало
"развёрнута боевой частью к игроку" (моя правка на визуал добавляла `Quaternion.LookRotation`
по этому — теперь корректно посчитанному — направлению, которое просто оказалось развёрнуто
на ~180°) и "летит из центра экрана" (объект, летящий почти вдоль оси камеры на близком
расстоянии, проецируется у центра кадра). Промах по врагу — по той же причине: пуля летела не
вперёд к цели, а фактически назад/вбок мимо неё.
Итоговое решение — не пытаться полностью убрать доворот (это опять сломало бы попадание на
обычных дистанциях, как в Update 1) и не оставлять его неограниченным (это и есть корень
проблемы). Вместо этого доворот **ограничен по максимальному углу** от направления, куда
физически смотрит ствол (`spawnPoint.forward`), через `Vector3.RotateTowards`:
- `WeaponController.GetShootDirection()` считает "сырое" направление на точку попадания, как
  и раньше, но затем ограничивает его `Vector3.RotateTowards(spawnPoint.forward, rawDirection,
  MaxAimCorrectionAngle (60°) в радианах, 0f)` — если нужная коррекция меньше 60°
  (подавляющее большинство обычных выстрелов на средней/дальней дистанции, доворот там всего
  несколько градусов), направление совпадает с точным прицеливанием один в один, ничего не
  меняется. Если нужна коррекция больше 60° (только экстремально близкий/вплотную враг),
  направление обрезается до 60° от `spawnPoint.forward` — никогда не назад, всегда в целом
  вперёд от дула, что почти гарантированно всё равно попадёт по вплотную стоящей (а значит
  занимающей большой угол обзора) цели.
- `BaseBulletsController.Initialize()` (правка из Update 1, `Quaternion.LookRotation` по
  направлению полёта) оставлена как есть — теперь безопасна, так как направление всегда
  ограничено ±60° от дула и никогда не развернёт модель к игроку.
Проверено рассуждением, что `spawnPoint.forward` — надёжный ориентир: иерархия в
`Player.prefab` — `Main Camera → GunsCamera → WeaponsHolder → *Holder → оружие →
*BulletSpawnPoint`, то есть спавн-поинт оружия физически привязан к камере и поворачивается
вместе с её питчем (`PlayerLook` крутит `playerCamera.transform.localRotation`) — не
статичный/независимый от прицела ориентир.
60° — это компромиссное число, не выверено плейтестом; если на практике вплотную стоящие
враги всё ещё иногда не получают урон или доворот всё ещё выглядит не идеально — нужно
подвигать `MaxAimCorrectionAngle` в `WeaponController.cs` и проверить в игре, а не гадать.
Файлы: `WeaponController.cs`.

Update 4 (2026-09-20): Update 3 убрал дикий визуальный излом, но урон вплотную стоящему врагу
всё ещё не засчитывался. Причина — сам подход "ограничить угол коррекции и понадеяться, что
физический снаряд долетит" фундаментально не может одновременно гарантировать и вменяемый
визуал, и попадание, когда дистанция до цели меньше смещения ствола от камеры. Ограниченного
(60°) доворота от направления взгляда камеры физически недостаточно, чтобы довести траекторию
до тонкого коллайдера близко стоящего врага (на скриншоте — скелет с явно нешироким
коллайдером): направление остаётся преимущественно вдоль взгляда камеры, а ствол при этом
смещён в сторону на фиксированное расстояние — снаряд пролетает мимо параллельным курсом,
просто уже не под диким углом, а визуально прилично.
Решение — разделить "нанесение урона" и "физический снаряд" на этой конкретной дистанции:
- `WeaponController.Shoot()` теперь считает прицельный луч (`Physics.Raycast` из камеры) один
  раз в начале и передаёт результат и в новый `ApplyPointBlankDamage(...)`, и в
  `GetShootDirection(...)` (раньше каждая функция делала свой собственный `Raycast` — убрал
  дублирование).
- `ApplyPointBlankDamage(...)`: если дистанция до цели меньше или равна реальному смещению
  ствола от камеры (тот же порог, что раньше использовался для клампа направления) — урон
  наносится НАПРЯМУЮ по результату прицельного луча камеры (`hit.collider.
  GetComponentInParent<HealthController>().TakeDamage(...)`), не дожидаясь и не полагаясь на
  то, попадёт ли физический снаряд в коллайдер. Прицельный луч камеры не имеет смещения (он и
  есть "откуда игрок смотрит"), поэтому на любой дистанции, включая нулевую, гарантированно
  указывает точно на то, во что целится игрок.
- Физический снаряд по-прежнему спавнится и летит с ограниченным (Update 3) направлением —
  чисто для визуальной целостности (мы не убрали и не изменили `GetShootDirection`). Если он

раньше, чем `PlayerSpawner.Start()` спавнит игрока (Unity гарантирует: все `Awake()` во всех
активных объектах отрабатывают раньше любого `Start()` в том же кадре). Значит, `Camera.main`
на момент прогрева — гарантированно `null`, и это `null` навсегда оседало в кэше `cam` у

подхватывает `Camera.main`, если он ещё `null` — за счёт постоянного повторного `Update()`
это самовосстанавливается, как только игрок реально появляется в сцене, независимо от того,
когда именно был создан конкретный инстанс из пула. Заодно заменил
`transform.forward = cam.transform.forward` на `transform.rotation = cam.transform.rotation`
— полное копирование поворота камеры надёжнее (не зависит от эффектов `LookRotation` с
дефолтным `Vector3.up`, в частности не может выродиться, если камера смотрит почти прямо
вверх/вниз).

(`Assets/Scripts/ObjectPool/ObjectPoolManager.cs`, `PoolableObject.cs`), от него отказались
в пользу прямых ссылок. Файлы — мёртвый груз, стоит либо удалить, либо, если идея ещё
рассматривается, дописать сюда почему вернулись к прямым ссылкам.
Последствия: нет общего лимита/статистики по всем пулам сразу; при затяжном бою пулы
только растут (см. Open-issue ниже).

### [Superseded by запись ниже] Конфиги оружия — ScriptableObject, но с "плавающим" рантайм-состоянием (2026-09-14)
Контекст: нужно было где-то хранить статичные данные оружия (урон, magazine size, префабы)
и per-run состояние (`CurrentAmmo`, `TotalAmmo`).
Решение (как было до фикса): `WeaponConfig : ScriptableObject` хранил `WeaponData[]` — а
`WeaponData` это **class**, то есть рантайм-мутации (`weaponData.CurrentAmmo--` в
`WeaponController.Shoot()`) писались прямо в поля ассета, а не в отдельную копию. Чтобы
ассет не оставался "грязным" между запусками Play Mode в редакторе, `WeaponConfig` сам
подписывался на `EditorApplication.playModeStateChanged` и откатывал `CurrentAmmo`/
`TotalAmmo` на `ExitingPlayMode`.
Последствия: это было узкое исправление симптома только для Editor Play-кнопки — не помогало
при обычном рестарте уровня в билде. См. фикс ниже — Open-issue #1 закрыт.

### [Accepted] Патроны оружия вынесены из WeaponData(ScriptableObject) в per-instance `WeaponRuntimeData` (2026-09-14)
Контекст: см. запись выше — `CurrentAmmo` хранился прямо в живом ассете `WeaponConfig`,
из-за чего магазин мог не сбрасываться при рестарте уровня (`AmmoManager` грузит `WeaponConfig`
через `Resources.LoadAll`, такие ассеты переживают обычную перезагрузку сцены).
Решение: `WeaponData.CurrentAmmo`/`MagazineSize` остаются как есть — это теперь просто
design-time дефолт ("сколько патронов в обойме при заходе на уровень"), в него больше никто
не пишет. Реальное мутируемое состояние живёт в новом `WeaponRuntimeData` — обычном C#-объекте,
который `WeaponController.Awake()` создаёт заново на каждый инстанс оружия, засеяв значением
из `weaponData.CurrentAmmo` (или `MagazineSize`, если 0). `IWeapon` получил метод
`AddAmmoToMagazine(int amount)` — через него `PlayerReload` пополняет магазин, не трогая
`WeaponData` напрямую. Заодно убран весь editor-хак из `WeaponConfig`
(`OnPlayModeStateChanged`/`ResetToDefaultRuntimeData`) — он больше не нужен, потому что
мутировать состояние ассета теперь просто негде в коде.
Файлы: `WeaponRuntimeData.cs` (переписан), `WeaponConfig.cs` (упрощён до чистого
контейнера данных), `WeaponController.cs`, `IWeapon.cs`, `PlayerReload.cs`,
`PlayerAutoReload.cs`, `RocketChamberPresenter.cs`.
Последствия: `WeaponData.TotalAmmo` (резерв патронов) не трогали — этот счётчик и так жил
только в `AmmoManager.ammoStorage` (Dictionary на MonoBehaviour-синглтоне), пересоздаваемом
заново при каждой загрузке сцены, и никогда не писался обратно в ассет — там утечки не было.
Не проверено вручную в редакторе/билде — рекомендуется прогнать плейтест "умереть → Retry"
и убедиться, что магазин каждый раз стартует с дефолтного значения.

### [Reconstructed] Разблокировка оружия по уровню + принудительная разблокировка (2026-09-14)
Контекст: не всё оружие доступно с самого начала, часть подбирается/открывается по мере
прогресса.
Решение: `WeaponUnlockManager` хранит `currentLevel` и таблицу `WeaponUnlockEntry`
(`gunsType → levelToUnlock, spawnAllowed`). `IsUnlocked()` разрешает оружие, если
`currentLevel >= levelToUnlock` **или** оно принудительно открыто через `UnlockNow()`
(используется, например, когда игрок явно подбирает предмет). `IsAllowedToSpawn()` —
отдельная проверка "можно ли этому оружию вообще появляться на уровне сейчас", независимая
от факта разблокировки.
Файлы: `Assets/Scripts/Weapons/WeaponCore/WeaponUnlockManager.cs`.
Последствия: `unlockedWeapons` (HashSet, только в памяти) не персистится между уровнями/сессиями
сам по себе — если нужна сквозная прогрессия между сценами, это должно приходить через
`Context`/`DataSystem`, а не через этот компонент.

### [Reconstructed] Input — New Input System, переключение action map через события, а не прямые вызовы (2026-09-14)
Контекст: нужно блокировать геймплейный ввод, когда открыт UI (пауза/game over), и наоборот.
Решение: `InputManager` (обёртка над `PlayerInput`) предоставляет типизированные `InputAction`
свойства и `SwitchToGameplayActionMap()/SwitchToUIActionMap()`. `ActionMapRequester` — тонкая
прослойка, которая держит "отложенный" запрос на смену карты (`pendingActionMap`), если
`InputManager` ещё не готов (актуально до того, как заспавнится игрок) и подписывается на
`PlayerSpawner.OnPlayerSpawned`, чтобы подхватить `InputManager` игрока сразу после спавна.
Файлы: `ActionMapRequester.cs`, `InputSystem/InputManager.cs`.
Последствия: имена action map'ов (`"GameplayActionMap"`, `"UIActionMap"`) сравниваются как
строки в двух разных местах (`ActionMapRequester.RequestActionMap` и `InputManager`
константы) — при переименовании в `.inputactions`-ассете нужно поправить оба места руками,
компилятор не подскажет.

### [Reconstructed] Иконки оружия — два взаимозаменяемых провайдера (Resources / Addressables) (2026-09-14)
Контекст: судя по `git log` (`add addressables`), проект начинался на `Resources.Load`,
затем часть перевели на Addressables, но не полностью.
Решение: `IWeaponIconProvider` реализован в двух вариантах — `ResourcesWeaponIconProvider`
и `AddressablesWeaponIconProvider`, конкретный назначается в инспекторе `WeaponIconManager`
через поле `MonoBehaviour providerComponent` (не строгую ссылку на интерфейс — так его можно
провалидировать в инспекторе). Если провайдер вообще не назначен, `WeaponIconManager` молча
падает обратно на прямой `Resources.Load<Sprite>($"WeaponIcons/{iconKey}")`.
Последствия: в проекте фактически два конкурирующих способа доставки иконок; при добавлении
нового оружия иконку нужно либо класть в `Resources/WeaponIcons`, либо регистрировать в
Addressables — в зависимости от того, какой провайдер стоит на конкретной сцене/префабе UI.
Явного единого стандарта в коде не закреплено.

### [Accepted] Git LFS: полная миграция истории (main + 4 активные ветки) (2026-09-15)
Контекст: `.git` весил ~924 МБ без Git LFS, тяжёлые бинарники (текстуры Portal Collection,
`Forest.hdr`, FBX-модели) были закоммичены напрямую в историю. См. запись выше про
`git lfs migrate` — не просто настройка на будущее, а именно переписывание уже
существующей истории.
Решение: смигрировали `*.png,*.jpg,*.jpeg,*.tga,*.tif,*.tiff,*.psd,*.exr,*.hdr,*.dds,*.bmp,
*.gif,*.wav,*.mp3,*.ogg,*.aiff,*.mp4,*.mov,*.fbx,*.obj,*.blend,*.max,*.ma,*.mb,*.ttf,*.otf,
*.unitypackage` (~516 МБ, 158 коммитов) в 5 веток: `main`, `refactor/stabilize`,
`AmmoBoxes`, `InputSystem`, `Pause`. 32 уже смёрженные ветки сознательно не трогали — их
содержимое и так полностью внутри `main`, переписывать нечего, только риск. Перед миграцией
сняли полный mirror-бэкап (`git clone --mirror`) в `D:\Unity\Projects\Gunvalanche_BACKUP_before_lfs.git`
— на случай отката. После миграции все 5 веток force-push'нуты на origin.
Важные грабли по пути (см. также вывод сессии):
- `git lfs migrate import` без `--everything` по умолчанию трогает только коммиты,
  которых ещё нет ни на одном remote — первая попытка почти ничего не мигрировала
  (переписала только 2 локальных ещё не запушенных коммита). С `--everything` заработало
  верно (158 коммитов).
- После миграции локальные файлы в рабочей копии стали LFS-pointer'ами (текст вместо
  бинарника), пока не запустили `git lfs checkout` — фильтр `smudge` не применился
  автоматически к уже вычекаученным файлам сразу после `migrate import`. После одного
  `git lfs checkout` обычные `git checkout` между ветками дальше смуджат корректно сами.
Последствия: `.git` локально временно вырос (~2.8 ГБ) — старые (домиграционные) объекты
всё ещё физически на диске, пока не сделан `git gc --prune=now` (не срочно). Любой другой
клон этого репозитория (другая машина) должен быть пересоздан или сделать
`git fetch && git reset --hard origin/<branch>` — историю переписали, старые локальные
копии разъедутся с origin. `git-lfs` должен быть установлен (`git lfs install`) на каждой
машине, которая будет с этим репозиторием работать.

### [Open, частично закрыто 2026-09-15] #2 — `ObjectPool.ExpandPool()` растёт без верхнего предела
`Assets/Scripts/ObjectPool/ObjectPool.cs:87-97`. Сам факт "пул растёт и не уменьшается
обратно" — осознанно не трогали, это trade-off (простота > память), решение по нему пока
отложено (`maxPoolSize` с предупреждением так и не заведён).
Но конкретный практический случай — реальный warning `ObjectPool: ShotgunBulletsPool is
empty, expanced pool.` в игре на 2-й волне — был не про архитектуру пула, а про
неправильный расчёт начального размера. `ShotgunBulletController.pelletsPerShot = 8`, а
`ShotgunBulletsPool.poolSize` был выставлен в 18 — то есть при полном расстреле магазина
(`MagazineSize: 6` в `Shotgun.asset`) в полёте одновременно может быть 6×8=48 дробинок
(с учётом `LifeTime: 4` в `BulletsConfig.asset` и перезарядки за 2с — дробинки предыдущего
магазина ещё живы, когда начинают лететь новые). 18 < 48 — пул неизбежно исчерпывался.
Для сравнения: `PistolBulletsPool` (10, магазин 7×1) и `RiffleBulletsPool` (31, магазин
30×1) — пул сопоставим с магазином, там всё верно, проблема была именно в том, что для
дробовика никто не учёл множитель "8 дробинок за выстрел" при выставлении `poolSize`.
Решение: `ShotgunBulletsPool.prefab` → `poolSize: 18` → `64` (48 = точный худший случай,
64 — с запасом на перекрытие при быстрой перезарядке). Сама архитектурная часть
(отсутствие верхнего предела у `ExpandPool()`) остаётся открытой — см. описание выше.

## Как добавлять новые записи

Когда принимаете архитектурное решение (новая система спавна, смена подхода к сохранениям,
переход на другой namespace для DI и т.п.) — добавьте запись сюда **в момент решения**,
а не постфактум. Три-пять строк контекста экономят часы реверс-инжиниринга в следующий раз.
